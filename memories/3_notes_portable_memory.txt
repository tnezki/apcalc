GENERIC MATH / SCIENCE NOTES BUILD - PORTABLE MEMORY v1
======================================================================

PURPOSE
======================================================================

This portable memory has TWO equal purposes.

PURPOSE 1 - FULL BUILD
Build a complete unit of student and teacher notes from the approved
upstream Assessment Plan and canonical Bank.

PURPOSE 2 - MAINTENANCE / REVISION
Repair, replace, revise, or rebuild one part of an existing notes
resource with the smallest necessary input, preserve everything the
user did not ask to change, run the same QA rules, and return the
complete updated replacement ZIP.

This PM is generic for:
  COURSE_FAMILY = MATH
  COURSE_FAMILY = SCIENCE

The same file/folder architecture is used for both course families.
Instructional content and representation choices branch naturally by
subject.

This PM assumes the course has already been built in this dependency
order:
  Framework -> Assessment Plan -> Bank -> Notes

The Notes build does NOT normally need the Framework again. The
Assessment Plan and Bank have already inherited the upstream alignment.

IMPORTANT PHILOSOPHY:
  Build order is not a classroom calendar.
  Notes are one instructional option in a rich course menu.
  Do not hard-code a teacher into a fixed Day 1 / Day 2 / Day 3 rhythm.

----------------------------------------------------------------------

Highest to lowest:

  2. Assessment Plan - learning target, I-cans, section scope,

  6. Optional approved supporting content supplied by the user
  7. Generic instructional inference only where sources are silent

Do not silently expand the section beyond the Assessment Plan.

PART 2 - READ ORDER / BUILD MEANS BUILD
======================================================================

READ ORDER - COMPLETE BEFORE WRITING STUDENT HTML
----------------------------------------------------------------------

1. Read this PM completely.
2. Read the entire Unit Assessment Plan.
3. Read unit[#]_mapping.csv completely enough to understand all Notes,
   Performance/Future Task, and Exit Ticket routing for every section.
4. Read the complete Notes and Performance/Future Task blocks in the
   Bank HTML for the unit.
5. Read the complete Bank items that will be used as the Notes exit
   ticket under the routing rule in this PM.
6. Inspect every Bank figure referenced by those items.
7. Read the Bank generate_graphs.py enough to locate the generation
   blocks for every reused Notes figure.
8. Read the uploaded authoritative graph_tool.py completely, including
   every public function signature and the FINAL append marker.
9. Complete the private UNIT NOTES PLAN and per-section CONTENT PLAN.
10. Only then write student HTML.
11. Run student QA.
12. Build teacher HTML from the final student HTML.
13. Run teacher/package QA.
14. Assemble the exact ZIP.

When the user says BUILD / CREATE / GENERATE / MAKE / COMPLETE NOTES,
execute the entire workflow. Do not stop after an outline or preview.

The ZIP is the normal endpoint.

PART 3 - COURSE-FAMILY BRANCH
======================================================================

DETERMINE COURSE FAMILY
----------------------------------------------------------------------

Prefer an explicit Assessment Plan declaration such as:
  Course Family: MATH
  Course Family: SCIENCE

If absent, infer only when the course is obvious. If genuinely
ambiguous, ask one short clarifying question.

MATH EMPHASIS
----------------------------------------------------------------------

Math notes should emphasize:
  - definitions and notation
  - symbolic structure
  - representation connections
  - equations / tables / graphs
  - worked reasoning
  - method selection
  - interpretation
  - justification
  - common algebraic/procedural misconceptions

Do not turn the reading into a dry procedure list. Explain why a method,
representation, theorem condition, or relationship works.

SCIENCE EMPHASIS
----------------------------------------------------------------------

Science notes should emphasize:
  - concepts and mechanisms
  - evidence and models
  - variables and relationships
  - diagrams / graphs / tables
  - observations vs. inferences when relevant
  - scientific explanation
  - quantitative relationships only when the Assessment Plan supports
    them
  - units, assumptions, and interpretation
  - common conceptual misconceptions

Do not force unnecessary calculation into conceptual science sections.

======================================================================
PART 4 - READING LEVEL / INSTRUCTIONAL DESIGN
======================================================================

DEFAULT READING LEVEL
----------------------------------------------------------------------

Target an approximately 11th-grade reading level unless the user or
course materials clearly specify a different level.

This does NOT mean making prose artificially dense.
Use mature, direct academic language with:
  - correct discipline vocabulary
  - clear sentences
  - meaningful transitions
  - enough explanation to support independent rereading
  - no unnecessary jargon
  - no childish simplification

For especially technical AP / advanced courses, preserve the exact
technical language students must learn.

GENERIC GOLD-STANDARD FLOW
----------------------------------------------------------------------

Use the Physics-style INTERLEAVED architecture for BOTH Math and Science:

  Learning Target
      -> Vocabulary
      -> Preview / skim
      -> What's To Come future task when the Bank supplies one
      -> Reading / Instruction Cycle 1
      -> Stop and Discuss
      -> Math Notes / Model Notes if needed
      -> Bank Example 1
      -> Bank You Try It 1
      -> Reading / Instruction Cycle 2
      -> Stop and Discuss
      -> Notes block if needed
      -> Bank Example 2
      -> Bank You Try It 2
      -> repeat as needed
      -> Vocabulary Definitions
      -> Summary
      -> Common Mistakes
      -> Exit Ticket

There is NO automatic Stop and Discuss after a You Try It.
Stop and Discuss belongs to the reading / representation / evidence
cycle, where students process meaning before application.

NUMBER OF CYCLES
----------------------------------------------------------------------

The Bank mapping controls the number of Notes Example/YTI pairs.

Use:
  - 1 cycle if the Bank has 1 pair
  - 2 cycles if the Bank has 2 pairs
  - 3 cycles if the Bank has 3 pairs
  - 4 cycles if the Bank has 4 pairs

Do not invent a fifth pair.
Do not drop a mapped pair merely to shorten the notes.

If the Bank intentionally has fewer than four pairs, that is valid.

READING DENSITY
----------------------------------------------------------------------

Each normal instructional cycle should usually contain:
  - 3 to 5 short paragraphs
  - about 2 to 5 sentences per paragraph
  - equations, tables, or approved figures where useful
  - one clear conceptual focus that prepares students for the paired
    Bank Example/YTI without solving those tasks for them

This is guidance, not a paragraph quota.

The notes should feel like a coherent instructional text plus guided
application, not a one-page summary followed by a worksheet.


======================================================================
PART 5 - BANK-FIRST CONTENT RULES - NON-NEGOTIABLE
======================================================================

THE BANK IS THE CANONICAL SOURCE OF STUDENT TASKS.
----------------------------------------------------------------------

Downstream Notes do NOT rewrite mapped Bank questions.

The following content is copied from the Bank VERBATIM in student
meaning, values, choice wording/order, tables, and figure intent:

  - Notes Examples
  - Notes You Try Its
  - Future / Performance preview task when used
  - Notes embedded Exit Ticket academic items

Allowed HTML normalization:
  - remove Bank-only metadata divs
  - remove visible Bank IDs
  - remove solution blocks from student HTML
  - convert destination-specific wrappers to Notes wrappers
  - remove a bank-only presentation class such as class="choices" while
    preserving the exact choices and order
  - keep table class="values"
  - preserve figure filename / visual exactly

Do NOT:
  - paraphrase a Bank prompt
  - swap numbers
  - alter answer choice wording or order
  - change the requested representation
  - simplify a multi-part prompt
  - change DOK by adding/removing reasoning requirements

NOTES EXAMPLE / YTI ROUTING
----------------------------------------------------------------------

Use mapping rows with:
  destination_group = notes

Expected IDs:
  U[#]-S[#]-NOTE-EX01
  U[#]-S[#]-NOTE-YTI01
  ...

Use destination_slot to preserve exact pair order.

Student HTML:
  copy the student-facing problem/task only.

Teacher HTML:
  use the Bank solution / rationale in the workspace immediately after
  the task.

FUTURE TASK ROUTING
----------------------------------------------------------------------

If a section has a mapping row such as:
  destination = performance_future_task
  destination_group = performance

use the section's first mapped future/performance task, normally PERF01,
as the What's To Come preview.

Expected ID pattern:
  U[#]-S[#]-PERF01

The student does NOT solve it here.
The purpose is long-range annotation and noticing.

If no performance/future task exists for the section:
  OMIT the entire What's To Come block.
  Do not invent one in Notes.

ASSESSMENT SECURITY
----------------------------------------------------------------------

Never pull student-facing content from:
  - formative assessment destination blocks
  - summative assessment destination blocks
  - assessment-only figures

into instructional Notes.

The Bank deliberately created unique assessment items. Preserve that
separation.

The explanatory reading may teach the concept, but must not reproduce
or effectively solve a future formative/summative item.

DISCUSSION PROMPTS ARE NOT BANK ITEMS
----------------------------------------------------------------------

Stop-and-Discuss prompts are instructional processing questions, not
assessment-bank questions.

They may be authored during the Notes build because their purpose is to
send students back to the reading, notation, evidence, diagram, or
representation they just studied.

Keep them concise and discussion-oriented.
Do not use them as hidden replacement assessment questions.

PART 6 - EXIT TICKET ROUTING FOR NOTES v1
======================================================================

GENERIC v1 CONVENTION
----------------------------------------------------------------------

Reserve Exit Ticket A from the Bank as the embedded Notes exit ticket.

Use the four ET-A items for the section, in mapping order:
  U[#]-S[#]-ET-A-C01
  U[#]-S[#]-ET-A-C02
  U[#]-S[#]-ET-A-L01
  U[#]-S[#]-ET-A-M01

All four are copied verbatim into the four exit-ticket cells.

This keeps the Notes exit ticket entirely Bank-authored and preserves
the Current / Last / Mastery spiral.

Future generic Exit Ticket PM default:
  ET-B and ET-C remain available as standalone optional exit tickets.

If this routing convention is intentionally changed later, update BOTH
this PM and the Exit Ticket PM so the same student item is not casually
reused in multiple destinations.

Do not invent reflection questions in place of the mapped ET-A items in
v1.

PART 7 - FIGURES / GRAPH TOOL - BANK FIGURES ARE AUTHORITATIVE
======================================================================

CORE RULE
----------------------------------------------------------------------

All student-task figures were created during the Bank build.
Notes COPY / REUSE approved Bank figures.
Notes do NOT independently redraw or redesign them.

For every Bank item used in Notes:
  1. Read figure_files in unit[#]_mapping.csv.
  2. Confirm the same figure reference appears in the Bank HTML item.
  3. Copy the exact PNG(s) from Bank figures/ into the section Notes
     figures/ folder.
  4. Preserve the filename exactly.
  5. Preserve neutral / non-answer-revealing captions and alt intent.

Only copy figures needed by the Notes section.
Do not copy formative/summative-only figures into student Notes.

READING / EXPLANATORY FIGURES
----------------------------------------------------------------------

A Bank Notes Example/YTI figure may also be referenced in nearby reading
ONLY when doing so does not reveal the answer to the upcoming task.

Prefer placing the figure with the canonical Bank task itself.
Use explanatory equations/tables/prose before the task rather than
showing an answer-revealing version of the figure early.

If a genuinely necessary NEW figure is missing from the Bank:
  STOP that part of the build.
  Report the missing figure need as a BANK MAINTENANCE issue.
  Do not create a Notes-only canonical student figure.

This protects the rule that figures are created upstream during Bank
construction.

GENERATE_GRAPHS.PY - REQUIRED IN EACH SECTION FOLDER
----------------------------------------------------------------------

The user's normal Notes package includes the graph tool for
reproducibility.

Each section folder must contain:
  generate_graphs.py
  figures/

generate_graphs.py is constructed as follows:

  1. Copy the currently uploaded authoritative graph_tool.py in full,
     byte-for-byte.
  2. Find the FINAL authoritative append marker.
  3. For each Bank figure reused by this Notes section, locate the exact
     generation block in the Bank package's generate_graphs.py.
  4. Append only those exact figure-generation blocks after the FINAL
     marker of the current graph tool.
  5. Do not alter graph parameters merely to make the figure look
     different in Notes.
  6. Do not add imports, OUTPUT_DIR changes, style overrides, or helper
     replacements to appended blocks.
  7. Run the section generate_graphs.py.
  8. Compare generated filenames with the copied Bank figure filenames.
  9. The regenerated figures must preserve the Bank visual intent.

If the section uses no Bank-generated figures:
  - still include generate_graphs.py as a verbatim copy of the uploaded
    graph_tool.py with no new generation blocks
  - still include an empty figures/ folder

This packaging rule is intentionally simple and stable.

GRAPH TOOL MISMATCH
----------------------------------------------------------------------

If the Bank generation block depends on a function not present in the
currently uploaded graph_tool.py:
  STOP and report the mismatch.
Do not patch the tool inside the Notes build.

PART 11 - REQUIRED SECTION SEQUENCE
======================================================================

Each section follows this order:

  1. TITLE
  2. LEARNING TARGET
  3. VOCABULARY - terms only
  4. PREVIEW - skim / vocabulary sort / noticed-predict-wonder
  5. WHAT'S TO COME - only when PERF/future task exists
  6. CONTENT HEADER
  7. READING CYCLE 1
       a. Reading / instruction
       b. Stop and Discuss + workspace
       c. Math Notes / Model Notes if needed
       d. Bank Example 1 + workspace
       e. Bank You Try It 1 + workspace
  8. READING CYCLE 2 - same pattern
  9. READING CYCLE 3 - same pattern if mapped
 10. READING CYCLE 4 - same pattern if mapped
 11. VOCABULARY DEFINITIONS
 12. SUMMARY + summary workspace
 13. COMMON MISTAKES
 14. EXIT TICKET - ET-A four-item bank ticket

Do not put all reading first and all practice later.
Do not insert an automatic Stop and Discuss after YTIs.

======================================================================
PART 13 - READING CONTENT RULES
======================================================================

WHAT READING MAY BE AUTHORED FROM
----------------------------------------------------------------------

Reading is authored from:
  - exact Assessment Plan Learning Target / I-cans
  - Key Vocabulary / Notation
  - Key Representations
  - Common Misconceptions
  - Modeling / Application Opportunities
  - Notes Example/YTI concepts and Bank solutions
  - approved Notes-item figures
  - optional user-supplied content sources if provided

The Bank solutions may inform explanatory accuracy, but do not copy a
solution sentence in a way that gives away the upcoming exact Example or
YTI.

READING MUST PREPARE, NOT PRE-SOLVE
----------------------------------------------------------------------

Before each Bank Example/YTI pair, explain the concept or method in a
different representation, generic case, or neutral example.

Avoid reusing the exact:
  - numbers
  - context
  - table values
  - graph features
  - answer choices
  - final conclusion

from the upcoming Bank item in the reading immediately before it.

The student should still have to solve the Bank task.

VOCABULARY BOLDING
----------------------------------------------------------------------

Inside instructional reading-box prose:
  - bold a vocabulary term only at its FIRST meaningful introduction
    and/or definition
  - if it appears incidentally earlier, wait until the meaningful intro
  - do not repeatedly bold it later
  - do not bold ordinary emphasis in reading prose

The term may be bold again in the final vocabulary definition table.

STOP AND DISCUSS
----------------------------------------------------------------------

Each reading cycle gets one Stop and Discuss with 2-3 prompts.

At least one prompt should require students to return to:
  - a sentence
  - equation
  - table
  - graph
  - diagram
  - model
  - comparison

Prompts should mostly be conceptual / interpretive and useful for oral
or written discourse.
Do not force DOK labels onto them.


======================================================================
PART 14 - REPRESENTATION RULES
======================================================================

MATH REPRESENTATIONS
----------------------------------------------------------------------

When the section naturally uses multiple representations, deliberately
connect them.

Possible artifacts:
  - MathJax equation / symbolic rule
  - table.values
  - approved Bank graph
  - verbal interpretation
  - context sentence

Examples:
  - function value: equation + table + graph meaning
  - limit: notation + graph/table behavior
  - derivative: symbolic notation + slope/rate interpretation
  - integral: area/accumulation + symbolic notation + units
  - theorem: hypotheses + conclusion + representation showing why
    conditions matter

Do not force all four representations into every cycle.
Use what serves the concept.

SCIENCE REPRESENTATIONS
----------------------------------------------------------------------

Possible artifacts:
  - variable / unit table
  - equation relationship
  - approved graph
  - data table
  - evidence/model diagram
  - verbal mechanism
  - observation/inference organization

Use equations as relationships/models first when that fits the course.
Do not exceed the Assessment Plan's intended quantitative depth.

ANSWER-REVEALING FIGURES
----------------------------------------------------------------------

Never add labels, captions, annotations, or highlighted features that
reveal what the student is supposed to identify, classify, infer,
critique, or calculate.

======================================================================
PART 21 - MAINTENANCE / REVISION MODE - PURPOSE 2
======================================================================

TRIGGER
----------------------------------------------------------------------

Use Maintenance / Revision Mode when the user says things such as:

  "I don't like the notes for 3.4. Rebuild them."
  "Reading 2 is too wordy."
  "The explanation before Example 3 is confusing."
  "The graph is too small."
  "Replace Example 2."
  "The teacher answer is wrong."
  "Fix the vocabulary section."

GOAL
----------------------------------------------------------------------

Make the smallest aligned change, preserve everything unrelated, and
return a complete replacement package.

Never make the user reconstruct the original build session.

MINIMAL-INPUT RULE
----------------------------------------------------------------------

Inspect what the user provides FIRST.
Ask only for genuinely missing authoritative sources.

If the user provides an existing Notes ZIP, recover from it:
  - section number/title
  - Learning Target / I-cans
  - data-source-id Bank IDs
  - figure filenames
  - student/teacher structure
  - current wording/layout

Then determine what else is actually necessary.

REVISION CLASSIFICATION
----------------------------------------------------------------------

A. NOTES-LEVEL REVISION
Examples:
  - reading wording
  - paragraph density
  - vocabulary explanation
  - Stop and Discuss prompt
  - Math Notes / Model Notes explanation
  - Summary
  - Common Mistakes
  - teacher facilitation note
  - figure placement / width class only

These can normally be revised in the Notes package without changing the
Bank, provided the Learning Target and mapped canonical tasks remain
unchanged.

B. BANK-DERIVED CONTENT REVISION
Examples:
  - replace Example 2 question
  - change You Try It 3 numbers
  - change ET-A question
  - alter future PERF task
  - alter a canonical Bank figure itself

Do NOT silently edit the Notes copy.
The canonical Bank must change first.

If the current Bank package + Bank PM are available, revise the Bank
first, then propagate the revised item verbatim into Notes.

If they are not available, ask only for the current unit Bank package
and the Bank PM needed to make the canonical change.

C. ASSESSMENT-PLAN ALIGNMENT REVISION
Examples:
  - Learning Target is wrong
  - I-can changed
  - section scope changed

Ask for the current Assessment Plan if it is not already available.
Do not invent a new target inside Notes.

D. PRESENTATION-ONLY FIGURE REVISION
Examples:
  - figure should be wider/narrower
  - move figure closer to related paragraph

If the underlying canonical figure is unchanged, this is a Notes-level
revision. Change only the HTML placement/approved wu-img width class.

Do not redraw the figure.

MAINTENANCE WORKFLOW
----------------------------------------------------------------------

1. INSPECT
   Open the existing Notes package completely enough to locate the
   requested section/block and its dependencies.

2. TRACE
   For any Bank-derived item, read data-source-id and trace it through
   mapping to the canonical Bank item.

3. CLASSIFY
   Decide A / B / C / D above.

4. PRESERVE
   Keep all unrelated sections and unrelated blocks unchanged.
   When practical, preserve untouched files byte-for-byte.

5. REVISE
   Make the smallest authoritative change.

6. PROPAGATE
   If a Bank item changed, update every supplied Notes occurrence of that
   Bank ID verbatim.

7. TEACHER SYNC
   Update teacher support wherever the changed student content affects
   an answer, rationale, misconception note, or follow-up.

8. FIGURE SYNC
   Copy/regenerate only affected figures. Do not regenerate unrelated
   figures merely because the ZIP is being rebuilt.

9. QA
   Run the relevant full-build passes plus complete package integrity.

10. DELIVER
   Return a complete replacement ZIP, not a loose HTML snippet.

DELIVERY SCOPE
----------------------------------------------------------------------

If the user gave a whole-unit Notes ZIP:
  return the whole updated unit ZIP unless they explicitly request only
  a section patch.

If the user gave only one section package:
  return u[unit]_[section]_notes.zip.

Briefly report:
  - section/block changed
  - Bank IDs changed, if any
  - whether Bank maintenance was required
  - affected figure(s), if any
  - QA result


======================================================================
PART 22 - COMMON FAILURE MODES - DO NOT DO THESE
======================================================================

1. Asking for the Framework during a normal Notes build.
2. Asking for AP Topic Questions during a normal Notes build.
3. Rewriting a canonical Bank Example or You Try It.
4. Swapping Bank numbers "to make it different."
5. Changing MC answer order from the Bank.
6. Pulling formative/summative items into Notes.
7. Creating a new student graph in Notes instead of fixing the Bank.
8. Redrawing an approved Bank figure independently.
9. Using the first graph-tool append marker instead of the FINAL marker.
10. Modifying graph_tool.py source lines.
11. Copying every Bank figure into every Notes section.
12. Making reading so explicit that it solves the upcoming Bank task.
13. Writing only a short intro and then dumping four pairs at the end.
14. Adding Stop and Discuss after every YTI by habit.
15. Forcing a Notes block before every pair.
16. Paraphrasing Learning Targets or I-cans.
17. Putting definitions in the opening vocabulary list.
18. Bolding every occurrence of vocabulary.
19. Bolding ordinary emphasis throughout reading prose.
20. Omitting the final Vocabulary Definitions table.
21. Writing generic Common Mistakes.
22. Using DOK labels as quotas inside Notes.
23. Forcing DOK 3/4 discussion questions where they are unnatural.
24. Embedding CSS or creating a new notes.css for content changes.
25. Using the wrong CSS path. BOTH are ../../css/...
26. Loading notes.css before base.css.
27. Using wrong MathJax delimiters.
28. Omitting figures/ because a section happens to have no figure.
29. Omitting generate_graphs.py from a normal unit Notes package.
30. Adding teacher answers to the student file.
31. Rebuilding the teacher file independently instead of copying the
    final student file.
32. Editing a Bank-derived question during Notes maintenance without
    updating the canonical Bank first.
33. Making the user re-upload every upstream source for a small repair.
34. Returning only a fragment when the user asked for a replacement ZIP.
35. Wrapping the unit ZIP in an extra notes/ or course/ directory.
36. Shipping __MACOSX, .DS_Store, or temporary build files.
